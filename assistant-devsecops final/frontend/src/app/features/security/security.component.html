Brique 3

Détection des vulnérabilités

Failles connues dans les dépendances, les images Docker et le code, triées par priorité et suivies jusqu'à leur correction.

Comment fonctionne cet écran ?

Trois outils alimentent la même liste ; chacun regarde un endroit différent :

  1. OWASP Dependency-Check — les bibliothèques Java du projet (pom.xml) comparées à la base publique des failles connues (CVE/NVD).
  2. Trivy — le contenu d'une image Docker : paquets du système et bibliothèques embarquées.
  3. SonarQube — le code source lui-même (injections, secrets en dur, bugs…), après une analyse mvn sonar:sonar.

À chaque nouveau résultat d'un outil, l'assistant compare avec ce qu'il connaissait déjà de cet outil : une faille jamais vue est créée au statut « Nouvelle » ; une faille qui n'apparaît plus passe automatiquement en « Corrigée (auto) » ; une faille corrigée qui réapparaît est rouverte avec l'étiquette « régression ».

Cycle de traitement : Nouvelle → En cours (« Prendre ») → Corrigée, ou bien Risque accepté / Faux positif avec une note justificative. Seules « Nouvelle » et « En cours » comptent comme ouvertes.

Colonne Prio. (0 à 100) : score CVSS × 8, +5 si la faille vient d'une dépendance ou d'une image (exposée à l'exécution), +8 si une version corrigée existe (correction facile), +1 par semaine d'ancienneté (max 7). Traitez la liste de haut en bas.

Quality gate : le pipeline est bloqué s'il reste une vulnérabilité critique ouverte, ou plus de 5 vulnérabilités hautes ouvertes.

Rôles : tout le monde peut consulter et demander une analyse IA ; lancer un scan, importer un rapport et changer un statut sont réservés au responsable qualité/sécurité et à l'administrateur.
